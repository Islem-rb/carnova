# Free deployment: Render + Neon

The public demo runs at no cost on two free plans:

| Piece | Service | Why |
| --- | --- | --- |
| App (API + Angular, one origin) | **Render** free web service, Docker | Runs the root `Dockerfile` as-is; HTTPS and a `*.onrender.com` address included |
| PostgreSQL | **Neon** free plan | Does not expire (Render's free Postgres is deleted after 30 days); pauses when idle |

Local development is unchanged: `docker compose up --build --wait` still runs Nginx, the backend, Postgres and Mailpit separately.

## How the hosted image differs from Compose

- **One service.** The root `Dockerfile` builds Angular, packages it inside the Spring Boot jar and lets Spring serve it (`SpaHosting`), with the same security headers Nginx sends locally. One origin means no CORS changes and one cold start instead of two.
- **Fast enough to wake on 0.1 CPU.** Render's free instance has 0.1 CPU and 512 MB. A plain Spring Boot start measured 233 s there; ahead-of-time processing (`-Paot`) plus a Class Data Sharing archive recorded at build time bring it to about 100 s, using ~175 MB of memory. Measured locally with `--cpus=0.1 --memory=512m`.
- **No email.** There is no mail service on the free demo (`MAIL_ENABLED=false`): reset and verification links are never sent, and the account pages say so. Email confirmation never gates access, so every other flow works.
- **Disposable uploads.** Free instances have no persistent disk. Photos and models uploaded by visitors disappear when the service restarts; the seeded demo listings use images bundled in the app and are unaffected.
- **Rate limiting per visitor.** The limiter reads `CF-Connecting-IP`, which Render's Cloudflare edge sets to the connecting address, replacing any value a client sends; `X-Forwarded-For` is never trusted because clients can prepend entries to it. Without the header it falls back to the socket address. Step 4 verifies this on the live service.

## One-time setup (about 10 minutes)

### 1. Stop the old Netlify previews (required)

`render.yaml` deploys a commit only when **every** GitHub check on it passes (`autoDeployTrigger: checksPass`). The old Netlify site `carnova-website` still builds this repository and fails, which would block every deploy. Either unlink the repository in Netlify (*Site configuration → Build & deploy → Link repository → Unlink*) or remove the repository from the Netlify GitHub app (*GitHub → Settings → Applications → Netlify → Configure*).

### 2. Create the database on Neon

1. Sign up at [neon.com](https://neon.com) (free plan) and create a project, region **AWS Europe Central 1 (Frankfurt)** to sit next to the Render service.
2. Open **Connect**, turn **off** connection pooling (Flyway and Hibernate want a direct connection), and copy the connection string. It looks like:

   ```text
   postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require&channel_binding=require
   ```

3. Split it into the three values Render asks for:

   | Render variable | Value |
   | --- | --- |
   | `DATABASE_URL` | `jdbc:postgresql://HOST/DBNAME?sslmode=require` |
   | `DATABASE_USER` | `USER` |
   | `DATABASE_PASSWORD` | `PASSWORD` |

The schema is created by Flyway on the first start; the demo catalogue and admin account are seeded once into the empty database.

### 3. Create the service on Render

1. Sign up at [render.com](https://render.com) with GitHub.
2. **New → Blueprint**, pick `Islem-rb/carnova`. Render reads `render.yaml`.
3. Fill in the values it asks for: the three database values above, and `DEMO_ADMIN_PASSWORD`, a new password for `admin@carnova.local` (not a password used anywhere else, and never one from the repository history). `JWT_SECRET` is generated by Render.
4. **Apply.** The first build takes several minutes; the first start then runs the migrations and seeds the demo.

From then on, every push to `main` deploys automatically once CI is green.

### 4. Check the live site

- Open `https://<service>.onrender.com`. The first visit after idle time wakes the service (about 1½–2 minutes on the free plan).
- `/api/meta` returns `"demo":true` and `"mail":false`.
- Sign in as `admin@carnova.local` and open `/admin`.
- Open `/studio`, then **Conduire**.
- **Check that visitors cannot forge their address** (it only uses up your own sign-in budget for one minute). Every request below claims a different fake IP. If the edge replaces the header, they all count as you and the last one is refused:

  ```bash
  url=https://<service>.onrender.com/api/auth/signin
  for i in $(seq 1 31); do
    curl -s -o /dev/null -w '%{http_code} ' -H "CF-Connecting-IP: 198.51.100.$i" \
      -H 'Content-Type: application/json' -d '{"email":"nobody@example.com","password":"wrong-password"}' "$url"
  done; echo
  ```

  Expected: thirty `401` then `429`. If all 31 are `401`, the header can be forged: set `CLIENT_IP_HEADER` to empty in Render (one shared budget, but not bypassable) and report it.

## Free-plan limits to keep in mind

- **Sleep:** the service stops after 15 minutes without traffic and needs about 100 s to come back. Lead with the demo video in the portfolio and label the live link "may take a minute to wake up".
- **Optional keep-awake:** a free uptime monitor (for example UptimeRobot) requesting `/actuator/health` every 5 minutes keeps it awake. One always-on service uses ~744 of the 750 free hours per month, so only do this for this single service. Render does not guarantee this behaviour. The health check never touches the database, so Neon can still pause.
- **Neon:** 1 GB storage and 100 compute-hours per month; the app opens at most four connections and drops idle ones after two minutes, so the database pauses when nobody is browsing.
- **Bandwidth:** the optional Datsun model is 71 MB per view; the default ToyCar is 5.8 MB.
- Payments stay in mock mode and the assistant in its offline mode.

## Reproduce the hosted setup locally

```bash
docker build -t carnova-render .
# then run it with --cpus=0.1 --memory=512m and the variables from render.yaml against any
# PostgreSQL 17. The CI job `render-image` builds this image and boots it with the same
# variables (512 MB, full CPU) on every push, then checks routes, headers, seeding and login.
```
